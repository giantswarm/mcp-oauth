# MCP 2026-07-28 authorization audit

Tracking issue: [giantswarm/mcp-oauth#701](https://github.com/giantswarm/mcp-oauth/issues/701).

Audit date: 2026-11-12. Library baseline: `e596b383f72784dfa8759d5a88d2e0f2b0835af0`.
The corrections below have regression tests; the remaining gaps prevent a full
authorization-conformance claim. Many also affect the 2025-11-25 profile.

## Scope and standards

The library implements authorization-server and protected-resource roles. Its
provider adapters also act as OAuth/OIDC clients to upstream identity providers.
It does not implement an MCP client, JSON-RPC version negotiation, or
`server/discover`. Those belong to the consuming MCP SDK and transport.

The audit uses the dated MCP profile and the drafts it references, rather than
substituting later draft revisions:

- [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery), [client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration), and [security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations).
- [OAuth 2.1 draft 13](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-13) and [CIMD draft 00](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-00).
- [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html), [RFC 8414](https://www.rfc-editor.org/rfc/rfc8414.html), [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html), [RFC 9207](https://www.rfc-editor.org/rfc/rfc9207.html), and [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728.html).
- [OIDC Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html), [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html), and [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html).

This is a source and regression-test audit, not a certification of deployments.
TLS termination, storage access controls, encryption, logging configuration, and
installation overrides need verification in the deployment that uses the library.

## Custom-scheme callbacks

Two distinct paths must not be conflated:

- CIMD metadata already rejects callback schemes other than HTTPS or HTTP
  loopback in `validateClientMetadataRedirectURIs`.
- DCR and pre-registered native OAuth clients can use custom schemes through
  `AllowedCustomSchemes`; `TrustedPublicRegistrationSchemes` separately controls
  token-free registration. `redirectAuthorizationCode` serves an interstitial
  for those callbacks.

The interstitial was introduced by [#102](https://github.com/giantswarm/mcp-oauth/pull/102)
and trusted-scheme registration by [#142](https://github.com/giantswarm/mcp-oauth/pull/142)
for desktop-client compatibility. Current [Cursor documentation](https://prod.cursor.com/docs/mcp#static-redirect-url)
lists HTTPS and localhost callbacks, and [VS Code documentation](https://code.visualstudio.com/api/extension-guides/ai/mcp)
lists loopback and HTTPS callbacks. Their current documented callbacks do not
require the old custom-scheme registration exception. Deployment configuration
still uses the Cursor scheme registration gate, so removing it also requires
checking which registration mechanism replaces it for current clients.

MCP's literal HTTPS/localhost redirect rule also appears in 2025-11-25, while
RFC 8252 section 7.1 and OAuth 2.1 section 8.4.3 permit private-use schemes for
native applications under additional requirements. This difference needs an
explicit applicability assessment. Empty chart defaults are not evidence that
installation overrides or older clients never use the feature. Inventory those
uses before proposing removal; no new compatibility mode is required by this
audit.

Enable the existing `EnableClientIDMetadataDocuments` setting explicitly in each
applicable consumer after checking its metadata-fetch network policy, TLS trust,
consent integration, and persistence. Preserve DCR where clients still need it.
Do not add CIMD configuration to a consumer that uses only OIDC utilities.

For every distinct authorization integration, verification needs real HTTP
authorization, code redemption, protected-resource access, applicable refresh,
and rejection paths. Shared fixtures are sufficient only when they exercise the
same integration path. Run build and configuration checks in every repository.
The existing metadata-only conformance work in [#695](https://github.com/giantswarm/mcp-oauth/pull/695)
does not cover browser authorization or consumer token forwarding.

## Completion

Keep #701 open until the applicable gaps are resolved, their fixes are released,
and consumer dependency/configuration updates have merged with the verification
above. Production rollout of every consumer is not a closure gate. SDK/transport
migration remains separate from authorization support.
